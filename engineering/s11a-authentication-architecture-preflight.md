# Sprint 11A — Authentication and identity architecture / preflight
Status: proposed architecture only; no backend, account, connection, token, identity record, provider credentials, deployed endpoint or real data. Canonical base 2255314627bd3ef058291eb64527c9fc13bb27b5. Implementation follows accepted 10C.5 and separately approved design. No change to existing demo identity or local storage. The browser's role/campus/membership selection is never authority.

## Decision proposal
Evaluate Planning Center OIDC first for member authentication, separate from provider API authorization. Official documentation confirms openid scope, authorization-code flow, discovery, ID-token claims (issuer, subject, audience, organization ID, nonce, expiration), and userinfo. It does NOT prove Citizen's ordinary Church Center participants can authenticate with the expected account experience, or that a person with an OIDC identity has Groups API access. Prove those in a nonproduction synthetic organization before committing to that approach. Alternative: managed identity provider with explicit administrator-approved mapping; no self-link by email/name. No final vendor choice or infrastructure spend approved.

## Trust boundaries
Browser -> same-origin backend-for-frontend (BFF) -> vetted OIDC library/identity provider; backend -> authorization service -> provider adapter -> minimized member view. Use HTTPS; client holds opaque Secure HttpOnly SameSite=Lax session cookie only. Never place provider or refresh token, raw identity claims, or protected data in localStorage, JS bundle, query parameters, analytics, logs or CDN cache. Isolate demo origin/session from authenticated environment; no automatic migration of fixture data. Do not reuse public preview as live environment.

## Proposed session flow
1. Backend initiates login; binds one-use unpredictable state, nonce, PKCE S256 verifier, exact registered callback and short transaction expiration to initiating browser. No arbitrary redirect target.
2. Exchange code server-side using library. Validate signature via trusted issuer discovery/JWKS, algorithm allowlist, issuer, audience, expiration, not-before if present, nonce, replay, subject, and organization claim. Reject unsigned, cross-tenant, missing/malformed identity and code replay. No client claim acceptance. Treat provider identity as issuer + subject + organization, not email, name, campus or UI role. Confirm provider subject-to-person mapping with official support/test data.
3. Require explicitly approved organization and pilot eligibility. Server establishes session via opaque random ID, rotates on login/privilege changes; server store only. Candidate 30-minute idle / 8-hour absolute lifetime, pending security approval. Cookie invalidation on logout; invalidate server session on consent revocation, role/tenant switch, identity mismatch, expiry or provider revocation. Revalidate group-level scope for every protected read; no authority from prior conversation.
4. A server-only verified-session constructor creates trusted input to existing pilot/s7-readonly-member-contract.cjs. Its current authenticated/serverVerified flags are not themselves proof. Restrict creation to authenticated middleware; use internal opaque capability or server record lookup, not JSON shape accepted over HTTP. Keep existing lib/member-context-contract.cjs demonstration schema exactly separate; later propose versioned live contract instead of setting identityVerified true in v1.
5. Consent is distinct from authentication: participant opts into the narrowly scoped pilot; church admin approves tenant/fields/role policies; deny if consent missing or withdrawn. No auto enrollment. Guest stays public.
6. Session expiry, logout, role change, missing permissions: purge protected in-memory member view and conversational history, close dialogs, cancel outstanding requests and ignore stale responses. No private cache fallback. Return neutral restricted/unavailable UI with reauthentication path. Do not retain raw care or message data.
7. Use explicit user gesture and anti-CSRF controls for session changes; no provider writes in pilot. Rate-limit login/callback, no open redirects; generic failure responses, structured non-PII reason codes.

## Required decisions / verification
- Identity provider and ordinary member login eligibility (including church users without staff permissions); pilot adults-only proposed, minor/guardian policy must be separately reviewed.
- Church organization ID and mapping authority; campus preference versus actual group authorization; handling multi-account, duplicate or merged records.
- Session infrastructure, secrets management, incident response, retention, deletion and account revocation. Proposed only; no vendor provisioning. Use isolated synthetic staging and dedicated environment secret store; never share keys in chat.
- Synthetic test matrix: valid login, expired/forged token, wrong issuer/audience/org, missing nonce, replay, wrong redirect, no membership, stale/revoked authorization, session fixation, logout and concurrent browser/account switch, provider failure, browser attempts to forge demo role. Verify no provider read occurs for denied session and no private UI/cache survives logout. No real data until 11C privacy/security and explicit 11E/F approval.
