# Connected beta v0.6

This branch adds invite-only email OTP authentication, server-checked sessions, group-scoped posts/comments/prayers/acknowledgements, leader-managed gatherings, RSVPs, limited leader member removal, and editable own display names. Fictional demo mode is the default without backend configuration. No demo content is uploaded. Bible reflections remain local and are scoped by account ID in beta mode.

Shared reads refresh on focus and every 15 seconds while visible; use Refresh for immediate reads. There is no realtime subscription, direct messaging or push delivery. Leaders cannot invite/promote users, remove leaders, inspect Bible reflections, or delete others' posts. Admission and roles are controlled by trusted operators. Old content by removed members remains in the group; display names may become “Former member”.

## Security and verification

Nine exposed tables have RLS and explicit column grants. Composite parent/group foreign keys protect comments, acknowledgements and RSVPs. Ownership and membership are checked on every operation. Membership/role decisions do not use user metadata. Invitation activation waits for Auth's trusted invited_at field; matching an email alone does not grant beta access. Session IDs are checked against auth.sessions, so sign-out, account disabling and membership removal revoke database access without waiting for JWT expiry.

Executed locally: 34 frontend/unit tests and the production build pass. The inherited compact-entry regex and the Bible browser heading assertion were corrected to match the approved compact interface. The existing five-width Bible browser suite also passes. Backend verification includes 78 transactional SQL policy assertions and 10 integration tests against real Supabase Auth v2.198.0, PostgREST v16.5 and PostgreSQL 17.6, with fictional accounts and a local email catcher. These cover anonymous denial, cross-group reads/writes, metadata escalation, parent/group mismatches, ownership, leader limits, shared content, RSVPs, email OTP, session persistence and old-token denial after sign-out. The official CLI full-stack image failed because the workspace ran out of disk. A smaller disposable test harness was used instead. A production-build browser smoke check also passed: two restored real Auth sessions shared posts, comments, prayers, acknowledgements and RSVPs; feed overflow checks passed at 320/375/390/430/980px. Hosted Supabase advisors, hosted auth/email settings and a complete connected mobile/accessibility audit still require verification; this is not a production security certification.

The SQL tests are in supabase/tests/security.sql. Run the dedicated localhost harness with `node scripts/beta-local.mjs start`, then `node scripts/test-beta-policies.mjs` and `node --test tests/beta/api.integration.mjs`. Stop only these disposable containers with `node scripts/beta-local.mjs stop`. For the connected browser smoke check, run `node scripts/build-beta-local.mjs`, start `npm run preview -- --port 4177`, then `node scripts/test-beta-browser.mjs`; rebuild without beta environment variables afterwards to restore the demo. The test harness creates random local credentials in ignored .beta-local/connection.json. They are never frontend service keys and never target a hosted project. Requires Docker, disk headroom and access to Alpine packages. Its localhost API adapter is for tests, not production. Normal Supabase CLI workflows remain available on a machine with enough space.

Types in src/features/beta/database.types.ts are introspected from the migration-backed test database by scripts/generate-beta-types.mjs. No schema queries or credentials are generated into client configuration. The client receives only the publishable/anon key. Invalid/partial beta configuration fails closed; builds reject service-role or secret keys. Build output generates a CSP allowing only the configured Supabase origin.

## One hosted setup checklist

1. Create a **dedicated private beta** Supabase project; do not apply these migrations to production or an unrelated existing schema. The connected account currently lists no projects; no external project was created. Apply versioned supabase/migrations SQL through your reviewed CLI/database workflow. Run the policy tests against a disposable staging copy and run Supabase security/performance advisors before admitting real users.
2. Keep **public signup disabled**, anonymous sign-in disabled, email confirmations enabled, refresh-token rotation enabled and JWT expiry reasonably short (local configuration uses one hour). Configure SMTP, rate limits and abuse protection appropriate to the pilot. Copy supabase/templates/invite.html and code.html into the hosted invitation and magic-link email templates. The app uses six-digit email codes and explicit token_hash invitation acceptance.
3. Set the Auth Site URL to the approved private beta origin, with exact redirect allow-list entries ending in `/`. The invitation callback is `/?token_hash=...&type=invite`. Avoid wildcard preview redirects. Verify actual delivered invitation and OTP emails before the pilot.
4. Using the trusted SQL editor/service backend, create a group, call `public.provision_beta_invitation(email, group_uuid, display_name, role)`, then use Auth Admin “Invite user”. Never expose the service key or provisioning RPC to the browser. Existing accounts can be assigned via trusted SQL insert into memberships; only operators should change roles. To disable beta access, set profiles.beta_enabled=false and revoke Auth sessions. An uninvited Auth admin invitation is intentionally rejected.
5. Configure `VITE_APP_MODE=beta`, `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` **only for the approved private beta site/context**. Never set a service-role/secret key in a VITE_ variable. Rebuild after changing configuration. Netlify reads netlify.toml and generated dist/_headers. PR deploy previews are forced to `VITE_APP_MODE=demo` in netlify.toml; use a separately protected beta branch/site context for live configuration; never point a public review preview at real member data. Protect the beta preview/site and review church-brand permission before distribution.
6. Validate two invited fictional accounts in one group on separate devices and an unrelated account in another group, then review consent/privacy/retention and account-deletion procedures before real-user admission. Local Bible notes are unencrypted on the device and are not recovered from Supabase. Deleting an Auth user with authored content requires an explicit content-retention/removal procedure; no unsafe automatic deletion endpoint is provided.

## Remaining limits

Hosted deployment, hosted policy/advisor tests, real-device email redirects and a full connected UI/accessibility audit are not completed. Feed reads currently cap at 50 posts/200 comments, requests at 100 and meetings at 50; no pagination UI is implemented. Check-ins are personal session reminders, not a persisted care ledger. Sensitive pastoral notes/moderation/admin invitation UI are intentionally not implemented. Network write errors can be ambiguous; the UI asks users to refresh before retrying. No production deployment or merge is authorized.
